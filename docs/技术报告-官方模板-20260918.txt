2、摘要
面向无屏 ESP32-P4 开发板，本作品将 openvela Agent 与 USB 控制台、以太网及可写存储集成，新增 device_info、network_status 两项工具，使模型可基于真实板端状态回答问题。同步 ask 结束后返回 NSH。围绕实际运行故障，完成任务栈、重叠堆、USB 缓冲、TLS 套件与时钟适配。已有实机问答和 GDB 截图，历史网络记录中网关与公网域名各 10 包测试均收到 10 包；这些是功能验证，不代表长期稳定性。项目复用上游芯片驱动和 Agent 框架，贡献聚焦跨层集成、工具扩展与证据化排障。
3、正文
3.1 绪论
应用场景是嵌入式开发者对无屏联网板卡的调试：需要通过多个系统命令了解内存、运行时间、IP 与网关，普通聊天接口却不知道设备的真实状态。本作品让模型调用只读状态工具并解释结果，减少人工拼接诊断信息的步骤。目标用户为具备命令行基础的开发者，不定位为医疗、安防或自动控制产品。
主要挑战是已有 NuttX 板级基础与 openvela Agent 的跨层约束：内建命令实际使用哪个任务栈；独立内核堆和用户堆是否重叠；USB 长命令与日志是否争用输出路径；Flash 文件名与可写目录是否匹配；TLS 套件和最终链接库是否一致；校时是否破坏超时统计；问答后是否交还 NSH。
创新与差异化是工程应用层面的组合：①将板端状态 API 转换为两项结构化 Agent 工具，不用模型猜测；②为无屏板卡实现同步 CLI 请求生命周期，而非启动后无法继续操作的假提示符；③用任务栈、异常寄存器和堆链表证据支撑移植修正，沉淀可复用开发 Skill。不宣称首个 ESP32-P4 适配，不把上游驱动或 ReAct 框架计为原创。
3.2 系统方案设计
系统由 ESP32-P4 Function EV 开发板、USB NSH、openvela ai_agent、板端只读工具、SmartFS 数据目录和华为 MaaS 服务组成。模型推理在云端，设备负责请求编排、工具执行、会话与状态采集。下图为逻辑模块及数据流。
选用已有 ESP32-P4 板卡和以太网，可在不增加传感器的情况下验证系统资源与通信状态。相较纯 NuttX NSH，增加 openvela Agent 语义交互；相较 PC 代读设备状态，工具实际运行在板端；相较端侧大模型，云端推理降低本原型的模型部署压力。断网时不提供离线推理，只能依靠 NSH 的 ifconfig、free、ps 等本地命令诊断；校时失败返回提示。弱网超时与重复请求恢复尚未完成系统性验收，不声称具有自动离线降级或自治修复。
通信为单板以太网到云端 HTTPS，无多设备协同。device_info 使用 uname、mallinfo、CLOCK_MONOTONIC；network_status 使用 netlib 查询 eth0、IP、网关、掩码和 MAC。工具输出 JSON，读取失败的地址字段为 null。UP、RUNNING 和 has_ipv4 仅是接口事实，不能证明外网或 DNS 正常。存储目录为 /data/agent，交互由 USB NSH 提供。
3.3 核心算法与技术原理
端侧不部署推理模型，因此不存在本项目的模型量化、端侧参数规模或推理加速声明。已接通华为 MaaS 的 OpenAI 兼容接口 https://api.modelarts-maas.com/v2/chat/completions，测试模型标识 deepseek-v4-flash，以 Authorization: Bearer <API_KEY> 鉴权。接口与模型以账号权限为准。使用 cJSON 组织请求、mbedTLS 提供 HTTPS；密钥不进入本报告和上传包。未使用 MiMo 推理作为本次演示后端。
复用 openvela Agent 的 ReAct 机制：请求模型，若返回工具调用则执行板端工具并将结果送回模型，直到形成文本回答或遇到错误。新增同步 agent_loop_ask 入口，复用核心初始化状态，结束后释放请求缓冲并返回 NSH；该模式不启动后台 cron、heartbeat、WebSocket。耗时计算改用 CLOCK_MONOTONIC，与 NTP 调整的实时时钟分离，避免时钟跳变引发虚假超时。
落地核心能力为 AI，具体使用 openvela packages_ai_agent 的模型代理、工具注册、上下文、会话与 ReAct 执行能力，不只使用 NuttX 内核。扩展包括两项设备工具、CLI 生命周期和配置/时间适配。改进建议是进一步区分板卡具备的工具与通用工具，完善平台级任务/堆配置检查及 TLS 证书验证。图形和多媒体未作为本作品的成果。
3.4 系统实现
固件由 nuttx（架构/板级/驱动）、apps（NSH 与网络初始化）和 packages/ai_agent 组成。项目增量见 source-changes/；开发 Skill 见 skills/esp32p4-openvela-bringup-debug/。既有芯片移植提交保留原作者信息，工作区增量另行归档。原始全量源码不放在上传 ZIP，评审从专属仓读取固定版本及补丁。当前源码归档不是已合入上游 PR 的声明。
启动完成控制台、procfs、存储和网络初始化。用户以 ai_agent ask 发起同步请求，准备核心组件和有效时间，执行模型/工具循环，返回后继续运行 NSH。配置命令不应无条件启动所有网络服务。下图为正常问答主流程；异常恢复和连续运行见测试边界。
板卡为 ESP32-P4 Function EV，利用板载以太网、SPI Flash 与原生 USB Serial/JTAG 控制台；外接仅 USB 线、网线、供电及已有路由器/交换机，无新增传感器或自制 PCB。关键 BOM：开发板 1 块、USB 数据线 1 根、以太网线 1 根、电脑和联网设备各 1 套，成本未核算。是否涉及硬件适配：是，基于已有 ESP32-P4 / NuttX / 社区工作做 openvela 集成，非声明该芯片首次适配。重点为 timer/EMAC 启动、DHCP、USB 缓冲和日志路径、SmartFS 以及 flat 模式任务栈与堆布局。照片中的其他随板部件不属于已验证功能。
实物照片：从参赛者已编辑 PPT 的第 1 页无修改提取；目前仅此角度，建议补后视/侧视照片。
交互端仅 USB NSH，没有新增移动端、图形 UI 或网关程序。使用 ai_agent ask <问题>，返回后继续 free / ifconfig / ps。演示中模型生成的“网络一切正常”等自然语言应以工具字段为准，不作为独立的互联网连通性证据。
自建开发 Skill：esp32p4-openvela-bringup-debug，存于专属仓 skills/ 下，供开发电脑上的 AI 编程助手使用。定义了匹配镜像/ELF、检查真实启动栈、定位堆自环、USB 队列与日志路径、文件名边界及 TLS/时钟的证据化流程，并附只读检查脚本。本次已验证 Skill 格式，运行脚本识别出 SmartFS 配置不一致。主选题为新硬件平台适配；板端 /data/agent/skills/ 仍是上游运行时机制及名称兼容修正，没有自建运行时 Skill，不将内置 Skill 计为原创。若按 AI 硬件产品创新方向申报，自建运行时 Skill 定义/触发验收仍需补齐，本报告不虚报完成。

3.7 总结与展望
完成一个基于 openvela Agent 的 ESP32-P4 CLI 诊断原型，接通云端问答并新增两项设备状态工具；围绕栈、堆、USB、TLS、时钟及存储边界做针对性修正，提供源码归档、开发 Skill、实物和调试证据。工作贡献以代码增量和实际证据说明，不以首发或全部代码原创作为宣传。
目标受众是嵌入式开发者、教学实验室和设备原型团队，主要场景为无屏板卡调试与联网设备状态解释。潜在价值是降低状态查询与诊断说明的门槛；后续可形成板卡适配服务、开发工具和教学案例。本次没有商业收入、付费用户或量产成本验证，不预测市场规模。面向不同设备扩展工具，需要逐板验证与安全边界设计。
下一步优先完成配置一致性、干净构建和连续运行测试、TLS 强验证、密钥管理、工具能力过滤及真实日志归集；之后再评估更丰富的设备工具。当前不增加未测试外设功能。申报前应确认视频语速、照片角度、团队信息、代码已推送至指定分支及日志完整性；本地材料存在不代表已在官网或 GitHub 提交。
